You are writing a handoff: a thorough account of the conversation so far that lets the work continue once the earlier messages are gone. Give the most weight to what the user explicitly asked for and to what you have already done. Keep the technical detail, such as code patterns, design choices and exact names, that someone picking up the work would need.

Before the handoff, think inside <analysis> tags so that nothing is missed. In the analysis:

1. Go through the conversation from start to finish. For each part, note:
   - what the user asked for and what they meant by it
   - how you approached it
   - the decisions made and the concepts involved
   - concrete detail: file names, full code where it matters, function signatures, edits
   - the errors you hit and how they were resolved
   - feedback from the user, above all any time they asked you to do something another way
2. Check your notes against the conversation for accuracy and gaps, and add what you missed.

The <handoff> block has these nine sections:

1. Requests and intent: every explicit request the user made and what they were after, in full detail.
2. Technical context: the important concepts, technologies and frameworks that came up.
3. Files and code: each file or code section that was examined, changed or created, why it matters and what changed. Favour the most recent messages, and give full snippets of code that a successor would need.
4. Problems and fixes: each error you ran into and how it was fixed, with any feedback the user gave about it, especially requests to do something another way.
5. Problems worked through: what has been solved, and any investigation still in progress.
6. User messages: every message the user wrote that is not a tool result. Together they show how the user's feedback and goals changed.
7. Open tasks: work the user explicitly asked for that is not done yet.
8. Work in progress: exactly what was being done just before this handoff was requested, with the latest messages from both sides in mind. Name the files involved and quote the code that matters.
9. Next step: the next action you would take, if there is one. It must follow directly from the user's most recent explicit request and from the work in section 8. If that work was finished, give a next step only when the user clearly asked for it, and never take up a side request or an old, finished one without checking with the user first. Whenever you give one, copy the most recent exchange verbatim, so that the task you were on and the point where it stopped cannot be misread.
